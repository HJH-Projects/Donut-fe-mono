# 병렬 작업(worktree) 운영 규칙

이 문서는 기능 단위 병렬 개발을 위한 로컬 worktree 규칙을 정의합니다.

## 1. 기본 흐름
- `dev` → `<type>/<description>` 생성
- 로컬 전용 하위 브랜치로 병렬 작업(원격 푸시 금지)

## 2. 하위 브랜치 예시
- `feat/auth-ui`
- `feat/auth-api`
- `feat/auth-state`

## 3. 통합 규칙
- 하위 브랜치 → `<type>/<description>` 순차 머지
- 충돌 해결은 상위 브랜치에서만 수행
- 통합 후 하위 브랜치 삭제

## 4. 문서 규칙
- 하위 브랜치에서 기능 상태표 수정 금지
- 문서 변경은 상위 브랜치에서 일괄 반영

## 5. 병렬 구현 가능 유형
- UI vs 로직: 화면 레이아웃/스타일 ↔ API 연동/상태 관리
- 기능 슬라이스: 소셜 로그인별, 탭별, 섹션별
- 컴포넌트 레벨: 공통 컴포넌트 제작 ↔ 페이지 조립
- 데이터 계층: API 클라이언트/모델 정의 ↔ 화면 바인딩
- 상태/검증: 유효성/폼 로직 ↔ 디자인/레이아웃
- 에러 처리: 에러 UI/빈 상태 ↔ 정상 흐름 UI

## 6. 병렬이 어려운 경우(순차 권장)
- 공통 타입/모델 확정 전 구현
- 동일 파일 동시 수정이 많은 경우
- 라우팅/구조 변경이 선행 조건일 때
