# 공통 개발 워크플로우

이 문서는 모노레포 공통 규칙을 정의합니다.
앱별 특수 규칙은 해당 앱의 `docs/`에 기록합니다.

## 1. 기능 진행 흐름
1) 작업 범위와 대상 앱을 확정합니다.
2) 최소 스펙을 먼저 작성합니다.
3) `dev`에서 `<type>/<description>` 브랜치를 생성합니다.
4) 구현 완료 후 **스펙을 보강**합니다.
5) 에이전트 작업 브랜치(`<type>/<description>-agent`)를 생성해 원격에 푸시하고, **스펙 보강 후** `<type>/<description>-agent` → `<type>/<description>` PR을 생성합니다.
6) `<type>/<description>`의 검증이 끝나면 `dev`로 머지합니다. (에이전트 자동화 범위 밖)

## 1.1 사전 확인(필수)
- 요청을 받으면 실행 전에 아래 항목을 요약해 사용자 확인을 받는다.
  - 역할(설계/구현/검수/통합)
  - 대상 앱
  - 기능 요약
  - 브랜치명(`<type>/<description>`)
  - 스펙 경로(`docs/<app>/spec_<endpoint>.md`)
- 사용자의 확인 이후에만 작업을 시작한다.
 - 설계/플랜 완료 시 **사용자 1회 검수**를 반드시 거친다.

## 2. 브랜치 규칙
- 기준 브랜치: `dev`
- 기능 브랜치: `<type>/<description>` (예: `feat/auth`, `fix/login-error`)
- 병렬 작업은 로컬 하위 브랜치 + worktree로 진행(상세는 WORKTREE.md)

## 3. PR 규칙
- PR 대상은 `<type>/<description>` 1뎁스 브랜치로 제한한다. (예: `feat/auth`)
- 에이전트 작업 브랜치는 `<type>/<description>-agent` 형식을 사용한다.
- 최종 PR(`<type>/<description>` → `dev`)은 상세 구현 나열을 피하고, **타이틀 중심 요약**으로 작성한다.
- PR 본문은 **섹션별 문단**으로만 구분한다. (예: UI / API / 상태 / 공통 / 검증)

## 3.1 커밋 규칙
- 커밋은 **항상 원자적 단위**로만 작성한다.
- 원자적 커밋 기준은 하나의 목적/맥락을 변경하는 범위로 제한한다.
- 원자적 커밋이 가능한 경우 사용자 확인 없이 진행한다.

## 4. 최소 스펙 기준
- 라우팅 구조
- 핵심 UI 구조
- 주요 API 계약

## 5. 검증 기준
- 빌드 성공 필수
- 린트/포맷은 앱별 기준 준수

## 6. 문서 업데이트
- 기능 상태표는 **`dev`에서만** 업데이트
- 에러 해결 기록은 앱별 로그에 추가
- 세션이 분리되어도 에러 로그는 **공유 자산**으로 유지한다. (동일 이슈 재발 방지)
- 정책 변경이 필요한 경우 `docs/policies.md`에만 반영한다.
- 작업 전/후 체크는 `docs/checklist.md`를 따른다.

## 7. 역할 분리(필수)
- 설계/플랜, 구현, 검수, 통합 역할은 분리 운영한다.
- 한 번의 실행에서는 **한 역할만** 수행한다. (역할 혼합 금지)
- 역할별 절차는 `docs/skill_*.md` 문서를 따른다.
 - 병렬 처리는 **구현 단계에서만** 허용한다. (설계/플랜, 검수, 통합은 순차 수행)

## 8. 예시 흐름 (역할별 실행 단위)
### A. 설계/플랜 에이전트
1) 문서 읽기: `docs/README.md`, `docs/workflow.md`, `docs/conventions.md`.\n
2) 대상 앱 확인 및 컨벤션 로드.\n
3) 기능 현황 확인.\n
4) 최소 스펙 작성/보완.\n
5) 작업 분해 및 핸드오프.\n

### B. 구현 에이전트
1) 문서 읽기 및 스펙 확인.\n
2) 할당된 작업만 구현.\n
3) 변경 내용 요약.\n

### C. 검수 에이전트
1) 스펙/컨벤션 준수 여부 검토.\n
2) 중복/누락/리스크 확인.\n
3) 피드백 정리.\n

### D. 통합 에이전트
1) 병합 및 충돌 해결.\n
2) 검증 수행.\n
3) 상태 업데이트.\n
